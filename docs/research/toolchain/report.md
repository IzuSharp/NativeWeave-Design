## 2. Actual implications of modern features for NativeWeave

The "recommendations" below are research directions for this round, not a final architecture already accepted through source, performance and cross-platform validation.

| Mechanism | Status in this round | Uses worth researching | Misinterpretations to avoid and validation obligations |
| --- | --- | --- | --- |
| C# 15 union types | Confirmed by stable documentation | Developer-facing success/failure/cancellation results and closed query nodes | The struct generated by a `union` declaration uses `object?` storage and boxes value-type cases; zero allocation cannot be promised, and it cannot serve as a C ABI union layout |
| Custom union / non-boxing access pattern | Described in the official C# 15 reference | Measure result types with explicit tags and value fields and `TryGetValue` access | Custom storage must meet official behavioral constraints; check default/null, case conversions, generic code size and AOT code generation; do not infer performance from syntax alone |
| Closed hierarchies | Confirmed by stable documentation | Domain states, query IR and compiler diagnostic objects | Direct descendants are closed within the same assembly; non-closed subclasses may still be inherited externally, so the entire inheritance tree must not be assumed automatically closed |
| Collection expression arguments, extension indexers and related features | Listed among stable C# 15 features | Reduce API usage overhead and internal code duplication | Use only where complexity is reduced; generator support, error diagnostics and the target compiler require compilation cases |
| New memory safety rules | **preview** | Evaluate pointer and ref safety rules in isolated experiments | Do not set production Core to `LangVersion=preview` to obtain them; the current stable Core must have an independent implementation path |
| Span/Memory/ref struct, value types and static abstract interface members | Research baseline of existing stable mechanisms | Synchronous borrowing, explicit memory ownership and static dispatch | Lifetimes must not cross prohibited await/callback boundaries; measure AOT generic instantiation, boxing and code size |
| `LibraryImport` source generation | Official stable mechanism | Static P/Invoke glue and reviewable marshalling | Successful generation does not imply ABI/lifetime safety; compare the actual supported scope of blittable `DllImport` and manual declarations rather than asserting that all DllImport is incompatible with AOT |
| Native AOT / trimming / static metadata | Production deployment mechanism | Publication and acceptance of production C# applications | `IsAotCompatible` is an analysis declaration, not execution evidence; each target requires execution after publish |
| Runtime Async V2 | **Canonical documentation still labels it preview** | Performance comparisons, exception stacks and ExecutionContext/AsyncLocal semantics | Runtime documentation describes NativeAOT/R2R support, but experiments on specific versions are still required; do not recast JIT-only optimization benefits as measured AOT benefits |
| .NET 11 built-in Zstandard / span compression APIs | Confirmed by official library documentation | Establish a .NET baseline if compression is selected as the synchronous engine validation module | A new Rust wrapper must explain its actual value relative to built-in libraries; missing capabilities in old versions cannot justify its introduction |
| Rust 2024 `unsafe extern`, unsafe attributes | Stable rules | FFI declarations, exported symbols and linking audits | Extern blocks declaring imported functions and exported functions use different syntax; record safety rationales for `no_mangle`/`export_name` |
| Rust 2024 `unsafe_op_in_unsafe_fn` | Default lint rule | Separate caller obligations from unsafe operations within function bodies | Explicit unsafe blocks cannot substitute for validity proofs, aliasing and release rules |
| Rust 1.99 raw-layout and ownership APIs | Confirmed by stable release notes | `Layout::for_value_raw`, `Box::into_non_null`, `Vec::into_parts` and related APIs reduce repeated glue | Check every API's safety preconditions; do not substitute a `Box::leak`-then-release pattern for clear ownership transfer |
| Rust 1.99 C variadic definitions | Stable, but not recommended as the default general-purpose ABI shape | Specific requirements when adapting existing C libraries | Availability does not imply adoption is appropriate; typed fixed-arity interfaces are easier to generate, analyze and verify across platforms |
| Rust 1.99.1 FFI bool fix | Confirmed by official patch notes | Include boolean ABI regressions in tests | Language-level type size differs from calling-register semantics; specify NativeWeave's boolean wire representation and validate across compilers |

Primary sources: [C# 15 feature list](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15), [Union reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/union), [P/Invoke source generation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke-source-generation), [AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [.NET 11 runtime](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime), [.NET 11 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries), [Rust 1.99.0](https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/), [unsafe extern](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html), [unsafe attributes](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-attributes.html), [unsafe operation lint](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html).

## 3. Verify AOT and target platforms in separate layers

The availability of a .NET SDK download for a platform does not imply that Native AOT, the selected Rust engine, native dependencies and NuGet packages jointly support it. Record build hosts, target OS/architecture, C runtime, minimum CPU, linking mode, engine dependencies and actual execution evidence separately.

Official AOT documentation explicitly restricts dynamic managed assembly loading and runtime code generation; expression trees have an interpreted execution path, so "Expression Trees cannot be used in AOT at all" is an overgeneralization. ORM research should examine expression construction, interpretation, SQL translation, dynamic compilation and metadata reachability separately. [AOT limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#limitations-of-native-aot-deployment)

Official cross-compilation guidance does not support ordinary cross-OS Native AOT builds; cross-compilation between some architectures on the same OS is possible with native toolchains. Windows and Linux acceptance therefore requires corresponding hosts and actual target execution; a successful script in this Linux environment cannot count as Windows success. [AOT cross-compilation](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/cross-compile)

.NET 11 runtime documentation changes some hardware baselines. ABI, distribution-package and benchmark records must pin CPU ISA conditions; this does not guarantee compatibility with every old machine merely because it is x64. [.NET 11 hardware requirements](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime#updated-minimum-hardware-requirements)

The Native AOT platform table still lists Android as experimental and notes the lack of built-in Java interop. iOS, MacCatalyst, GUI native shells and related areas require separate platform topics; do not infer complete mobile UI maturity from desktop/server AOT. [AOT platform restrictions](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#platformarchitecture-restrictions)

A Rust announcement already describes future 1.100.0 changes to i686 Windows host tools; this is a host-tool change and must not be misreported as an inability to generate all 32-bit Windows targets. Recheck against the version actually adopted. [i686 host-tool adjustment](https://blog.rust-lang.org/2026/10/02/demoting-i686-windows-targets-to-std-only/)

## 6. Recommended version governance (pending ADR review)

Pin the verified SDK in `global.json` for research snapshots and the exact Rust release in `rust-toolchain.toml`; toolchain upgrades use independent PRs with release facts, differences, affected targets and regression records. Dependency locking, SDK pins, Rust MSRV, edition and engine ABI versions are distinct concepts and are maintained separately.

Do not commit `latest`, uncontrolled nightly or `LangVersion=preview` as a production baseline. A support lifecycle does not mean a pinned patch is never updated; official .NET policy requires following servicing during support. Whether to support .NET 10 LTS, a lower Rust MSRV or an old RID belongs to requirements and cost research; the initial fact-verification round must not automatically expand product commitments.
