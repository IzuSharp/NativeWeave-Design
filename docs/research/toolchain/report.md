## 2. Actual Implications of Modern Features for NativeWeave

All "recommendations" below are research directions for this round, not a final architecture that has passed source, performance, and cross-platform acceptance.

| Mechanism | Status in this round | Uses worth researching | Misinterpretations to avoid and validation obligations |
| --- | --- | --- | --- |
| C# 15 union types | Verifiable in stable documentation | Developer-facing success/failure/cancellation results and closed query nodes | A struct generated by a `union` declaration uses `object?` storage and boxes value-type cases; zero allocation cannot be promised directly, and this is not a C ABI union layout |
| Custom union / non-boxing access pattern | Described in the official C# 15 reference | Measure result types with explicit tags and value fields, and `TryGetValue` access | Custom storage must meet the official behavioral constraints; check default/null, case conversions, generic code size, and AOT code generation; performance cannot be inferred from syntax alone |
| Closed hierarchies | Verifiable in stable documentation | Domain states, query IR, compiler diagnostic objects | Direct descendants are closed within the same assembly; a non-closed subclass may still be derived from externally, so the entire inheritance tree must not be assumed automatically closed |
| Collection expression arguments, extension indexers, etc. | Listed as stable C# 15 features | Reduce API usage complexity and internal code repetition | Use only when they reduce complexity; generator support, error diagnostics, and the target compiler must have compilation cases |
| New memory safety rules | **preview** | Evaluate pointer and ref safety rules in isolated experiments | Do not set production Core to `LangVersion=preview` to obtain them; the current stable Core must have an independent implementation path |
| Span/Memory/ref struct, value types, static abstract interface members | Research baseline of existing stable mechanisms | Synchronous borrowing, explicit memory ownership, static dispatch | Lifetimes cannot cross disallowed await/callback boundaries; AOT generic instantiation, boxing, and code size must be measured |
| `LibraryImport` source generation | Official stable mechanism | Static P/Invoke glue and reviewable marshalling | Successful generation does not establish ABI/lifetime safety; compare the actual support scope of blittable `DllImport` and handwritten declarations rather than asserting that all DllImport is unsupported by AOT |
| Native AOT / trimming / static metadata | Formal deployment mechanism | Publication and acceptance of production C# applications | `IsAotCompatible` is an analysis declaration, not execution evidence; each target requires execution after publish |
| Runtime Async V2 | **Canonical documentation still marks it preview** | Performance comparisons, exception stacks, ExecutionContext/AsyncLocal semantics | Runtime documentation describes NativeAOT/R2R support, but experiments with specific versions are still required; JIT-only optimization gains must not be recast as measured AOT gains |
| .NET 11 built-in Zstandard / span compression APIs | Verifiable in official library documentation | Establish a .NET baseline if compression is selected as a synchronous-engine validation module | A new Rust wrapper must explain its actual value relative to the built-in library; capabilities missing from older versions cannot justify its introduction |
| Rust 2024 `unsafe extern`, unsafe attributes | Stable rules | FFI declarations, exported symbols, linking audits | An extern block declaring imported functions and an exported function use different syntax; the safety rationale for `no_mangle`/`export_name` should be recorded |
| Rust 2024 `unsafe_op_in_unsafe_fn` | Default lint rule | Separate caller obligations from unsafe operations in the function body | An explicit unsafe block does not replace validity proofs, aliasing rules, or release rules |
| Rust 1.99 raw-layout and ownership APIs | Verifiable in stable release notes | `Layout::for_value_raw`, `Box::into_non_null`, `Vec::into_parts`, etc. reduce glue repetition | Check each API's safety preconditions; do not substitute a `Box::leak`-then-release pattern for clear ownership transfer |
| Rust 1.99 C variadic definitions | Stabilized, but not recommended as the default general-purpose ABI shape | Specific adaptation needs for existing C libraries | Availability does not mean it should be introduced; typed fixed-arity interfaces are easier to generate, analyze, and verify across platforms |
| Rust 1.99.1 FFI bool fix | Verifiable in official patch notes | Include Boolean ABI regressions in tests | Language-level type sizes differ from calling-register semantics; specify NativeWeave's Boolean wire representation and verify it across compilers |

Primary sources: [C# 15 feature list](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15), [Union reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/union), [P/Invoke source generation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke-source-generation), [AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [.NET 11 runtime](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime), [.NET 11 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries), [Rust 1.99.0](https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/), [unsafe extern](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html), [unsafe attributes](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-attributes.html), [unsafe operation lint](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html).

## 3. AOT and Target Platforms Must Be Verified in Layers

The availability of a .NET SDK download for a platform does not establish that Native AOT, the selected Rust engine, native dependencies, and NuGet packages jointly support that platform. Record the build host, target OS/architecture, C runtime, minimum CPU, linkage, engine dependencies, and actual execution evidence separately.

Official AOT documentation explicitly limits dynamic managed assembly loading and runtime code generation; expression trees have an interpreted execution path, so "Expression Trees cannot be used under AOT at all" is an overgeneralization. ORM research should separately examine expression construction, interpretation, SQL translation, dynamic compilation, and metadata reachability. [AOT limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#limitations-of-native-aot-deployment)

The official cross-compilation guidance does not support conventional cross-OS Native AOT builds; cross-compilation between some architectures on the same OS is possible with the required native toolchain. Windows and Linux acceptance therefore requires the corresponding hosts and actual target execution; a successful script in this Linux environment is not a Windows success. [AOT cross-compilation](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/cross-compile)

The .NET 11 runtime documentation changes some hardware baselines. ABI, release package, and benchmark records must pin CPU ISA conditions; this is not a guarantee that any x64 machine, including all older machines, is compatible. [.NET 11 hardware requirements](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime#updated-minimum-hardware-requirements)

The Native AOT platform table still lists Android as experimental and notes the absence of built-in Java interop. iOS, MacCatalyst, GUI native shells, and similar areas require separate platform topics; complete mobile UI maturity cannot be extrapolated from desktop/server AOT. [AOT platform restrictions](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#platformarchitecture-restrictions)

A Rust announcement has already described the future 1.100.0 adjustment to i686 Windows host tools; this is a host-tool change and must not be misrepresented as loss of the ability to generate all 32-bit Windows targets. Recheck against the version actually adopted. [i686 host-tool adjustment](https://blog.rust-lang.org/2026/10/02/demoting-i686-windows-targets-to-std-only/)

## 6. Recommended Version Governance (Pending ADR Review)

Research snapshots pin the verified SDK in `global.json` and the exact Rust release in `rust-toolchain.toml`; toolchain upgrades go through separate PRs with release facts, differences, affected targets, and regression records. Dependency locking, SDK pins, Rust MSRV, edition, and engine ABI version are distinct concepts and are maintained separately.

Do not commit `latest`, uncontrolled nightly, or `LangVersion=preview` as a production baseline. A support period does not mean a pinned patch is never updated; official .NET policy requires following servicing updates during support. Whether to support .NET 10 LTS, a lower Rust MSRV, or an older RID is left to requirements and cost research, and cannot automatically expand product commitments during initial fact verification.
