# D03 — Narrow binding description, generated imports and diagnostics

Contract: **C-BINDING-001@0.3.0**. Complete research/design candidate; the registry records the exact reviewed version/hash and acceptance. Product verification remains in Delivery. Research inputs: R03–R06, R07–R11. Future owners: A09–A12, B09/B10/B12. This specification creates no SQL AST, ORM translator, HTTP stack or global runtime in C#.

## 1. Decision and reuse

Native adapters expose a small, explicit C ABI over mature Rust engine APIs. The adapter's Rust exported declarations are the representation authority; a versioned semantic sidecar supplies information Rust/C syntax cannot express: owner/release pairing, borrow duration, logical admission, allowed thread and callback retirement. A build tool checks that the two agree and emits a **build-time binding description**. That description is not a runtime protocol or domain query language.

Use .NET's maintained `LibraryImportGenerator` for static managed import stubs. Its actual v11 implementation uses attribute-driven incremental discovery, validation and value-comparable generation stages. Do not recreate its marshaller. The NativeWeave tool emits the constrained declarations and resource wrappers around those stubs; raw blittable `DllImport` remains a permitted implementation mechanism when generated by a proven existing tool and covered by the same layout/entry tests. DllImport is not intrinsically incompatible with Native AOT.

Maintainer-side csbindgen is suitable for primitive raw Rust-to-C# declaration extraction, with an obligatory completeness check. At pinned csbindgen 1.9.8, parser paths can print a message and omit an unsupported function. Omission is a build error when the export is in the declared inventory. cbindgen is an independent Rust-to-C-header route, useful for C compiler layout probes; bindgen goes in the opposite direction, C/C++ to Rust. Neither supplies the managed lifetime contract automatically.

Do not adopt a large universal generator/runtime simply to obtain callbacks. Current Diplomat really has a .NET backend, but its actual pinned templates use DllImport despite a guide saying LibraryImport; its callback lowering is disabled/incomplete and its ownership profile requires application synchronization of call/Dispose. Those constraints do not satisfy D04/D05 automatically. Interoptopus has real first-class C# inventory/model support; its high-level Task shape alone does not establish NativeWeave retirement and admission semantics. UniFFI's poll/store/wake implementation is valuable source evidence, but its official C# backend is third-party. Their future adoption is a replaceable maintainer implementation choice subject to conformance, not a new application dependency or reason to defer the ABI.

Exact upstream commits, files, ranges and limitations are in [source-inspection](../../verification/interop-completion/source-inspection.json) and [R05](../research/topics/R05/report.md). The same research export is compared through csbindgen DllImport and LibraryImport in `experiments/interop-completion/binding_probe.py`; inspect its actual result before claiming execution on a platform.

## 2. Binding description contents

The normalized description contains only:

| Element | Required fields and invariants |
|---|---|
| Module | Stable module ID, ABI major/minor, target RID/triple, upstream/version/feature identity, generated input digest |
| Wire record | Field names and fixed-width types, target sizes/alignments/offsets, defined reserved fields; no unmanaged padding as semantic data |
| Export | Exact symbol, C calling convention, status/result storage, parameter direction/nullability, required capability, availability by target |
| Owner | Opaque kind, creating module, exactly one release function, optional explicit clone, parent-state owner relation |
| Borrow | Validity end: call, callback, retained owner or operation retirement; mutable/exclusive flag; finite size and overflow checks |
| Operation | create/start/request_cancel/take_result/try_retire/release functions and D06 state mapping |
| Callback | Blittable UCO signature, cookie position, notification ownership, reentrancy, D05 close/drain contract |
| Thread profile | Free-threaded, serialized, owner-thread or externally driven; release executor and close progress obligation |

Example **design data, not a compiled full product schema**:

```json
{
  "schema": 1,
  "module": "database",
  "abi_major": 1,
  "export": "nw_database_query_start_v1",
  "calling_convention": "C",
  "return": "status_u32",
  "inputs": [
    {"name":"operation","type":"opaque:query","borrow":"call"},
    {"name":"parameters","type":"bytes_view_v1","borrow":"call","copy_before_accept":true}
  ],
  "acceptance": "D06.start",
  "required_capability": "database.query.v1"
}
```

The example's identifiers are illustrative; the domain specification owns its final function inventory. Unknown schema versions, types, owner kinds, capability IDs and unmatched release functions are hard errors. No arbitrary custom code snippet is executed while reading the description. The native binary's ABI metadata and packaged descriptor digest are checked before the first domain operation.

## 3. Maintainer build and ordinary consumption

1. Pin Rust/.NET tools, upstream source, feature set and adapter source. Parse only the exported adapter surface; private SeaQuery/SQLx/Hyper/Tokio types stay private.
2. Normalize declarations and semantic sidecar. Reject unsupported syntax instead of guessing. Verify the expected export inventory against parsed, generated and linked symbols, including target-conditional exports.
3. Emit C header, Rust assertions/ABI-info data, C# raw declarations, typed SafeHandle wrappers and diagnostics metadata. Render output deterministically: stable ordinal ordering, fixed newline policy, no paths/timestamps/random IDs in generated API text.
4. Compile both languages and a C layout probe for each target. Compare every public record's size/alignment/offset and every export signature. Pin tool/output hashes in the native package manifest.
5. Publish managed APIs and matching precompiled native assets. A normal consuming application executes `dotnet build`, `dotnet run` and `dotnet publish -r <rid> -p:PublishAot=true` without Cargo or generator execution that recompiles Rust.

Adding a C# Entity changes only bounded managed static metadata/descriptors and DTO mapping. It does not change the generic native database module. Extending native engine capabilities is a maintainer release, not an entity-build hook. No source generator performs network I/O, starts Cargo, consults a database or depends on a mutable local native build directory.

## 4. Roslyn pipeline

Application generation is optional: manually supplied typed metadata has identical semantics. For generated descriptors use `ForAttributeWithMetadataName` on explicit sealed marker attributes. Extract compact, value-equatable models from symbols immediately; do not retain Compilation, ISymbol, SyntaxNode or Location in long-lived shape models. A location needed for diagnostics is handled separately from the semantic cache key. Arrays require element-wise equality; records containing arrays do not gain it automatically.

Inputs include relevant target/configuration options, ABI description hash and semantic entity shape. Unrelated source edits must preserve descriptor bytes. Two types with the same short name use collision-free fully qualified identities; deterministic escaping handles generic/nested types and namespaces. Reject open generic entity metadata without an explicitly supported closed-use policy. Respect cancellation tokens in transforms and never publish partial generated output as a successful result.

Generators run against the same input compilation. They cannot rely on another generator's ordinary output in the same pass. Therefore NativeWeave does **not** emit `[LibraryImport]` declarations from an application generator expecting the framework generator to consume them in that pass. Raw engine bindings are generated during maintainer build and compiled into the shipped assembly, or generated before C# compilation by the build tool. Application SG emits static entity/DTO code that has no second-generation dependency. The executed Roslyn probe contains a negative peer-generator observation and a positive descriptor pipeline.

## 5. Generated lifetime and error code

Raw imports are internal and contain no managed string/object/bool ABI parameters. Generate `byte`, fixed-width integers, explicit pointers and size-prefixed records from D02. UCO entry points are static, nongeneric and use exact unmanaged calling convention with blittable fields. Do not set SuppressGCTransition on callbacks, blocking calls, allocation, lock acquisition or reentrant engine work; any future leaf-call exception needs independent justification and measurement.

Each public owner wrapper follows D04: in one short gate check Open and obtain SafeHandle AddRef; then call FFI outside the gate and release in finally. Closing flips admission under the same gate. Physical SafeHandle lifetime does not implement logical closure or mutable exclusivity. Return views keep a lease during a scoped consumer callback; do not return naked Span after releasing the owner.

Async wrappers reserve all operation/mailbox/input capacity before native acceptance, install a stable GCHandle cookie, create and start separately, and retain the setup/control leases through return. Static callbacks catch ordinary managed exceptions, publish a preallocated fault latch and wake the existing completion slot. They do not invoke user code. The coordinator performs typed take once and D06 retirement; constructor, marshalling and DTO exceptions unwind only within C# and return all acquired owners. Native Result/status failures and panic poisoning remain D08 responsibilities.

## 6. Stable diagnostics

| Diagnostic class | Reject before execution |
|---|---|
| NWABI001 | Unsupported wire type, bool/char marshalling ambiguity, Rust-private layout, implicit string encoding |
| NWABI002 | Size/offset/calling-convention mismatch, unknown ABI schema, missing linked export |
| NWOWN001 | Missing/wrong-module destructor, owner transferred on failure, escaping borrowed result |
| NWASYNC001 | Async input with only a call-scoped pin; callback without retirement authority |
| NWMODEL001 | Unsupported entity member/codec, duplicate native field ID, open generic metadata |
| NWGEN001 | Ambiguous generated identity, conflicting hint name, nondeterministic or stale binding inputs |

Diagnostic IDs above are reserved design IDs; the experiment's `NWPROBE001` is deliberately separate. Diagnostics must show the offending symbol/location, rejected mechanism and supported alternative. Never globally suppress AOT/trimming or generator diagnostics to make a package build.

## 7. Verification and ownership

A09 owns normalized ABI-description validation and inventory equivalence; A10 C# emission and descriptor digest; A11 Rust exports/layout assertions; A12 diagnostics and unsupported input fixtures. Their file scopes remain the existing Plan scopes. B10 owns optional entity/DTO metadata, B12 typed materialization, B11 native query translation; no generator task owns SeaQuery or SQL dialect logic.

Required product tests: missing/duplicate symbols; unsupported type omitted by upstream generator; namespace/generic-name collision; entity addition with unchanged native binary hash; same input byte-for-byte output; one-field edit affecting exactly its descriptor; malformed sidecar; cancelled generator pass; compatible/old ABI package pairs; Windows/Linux normal/AOT independent NuGet consumption. Normal, diagnostic and AOT results are recorded separately. Current research establishes the pipeline choice and counterexamples; the complete generator remains future A09–A12 implementation.

## 8. Acceptance boundary

The research/design question is resolved by the explicit, independently reviewable pipeline and actual primitive-binding/SG/AOT probes. Product completeness, full schema code generation, every diagnostic, IDE distribution, two-OS package conformance and long-term compatibility are future Delivery obligations. Those obligations must not be treated as prerequisites to accepting the design that specifies them.
